Top theme: the fail-closed, positive-evidence discipline that the recent commits
(d43b373, b670b8a, 1862aa7) built into change detection is not applied uniformly.

### High

- **2.2** `[sec]` `builder.py:311-315`, `:334-336`, `:392-418`, `:959-966` - Targeted
  `POST /refresh {"files": [...]}` (`daemon.py:977-980`) reaches
  `IndexBuilder.refresh(files=...)`, which validates only path containment
  (`_validate_repo_relative`) and then sets `changed_files = [(f, "update") for f in files]`.
  The Phase 1 loop calls `_reindex_file_preserving` -> `_index_file` ->
  `_read_file_content`, which reads the whole file. Neither `_is_excluded` nor the
  `max_file_size` check runs; both live only in `_classify_candidates`
  (`builder.py:856-905`), which this path never calls. Why it matters: the default
  exclusion set (`config.py:12-30`) exists to keep secrets files, lockfiles, and build
  output out of the index. A token holder, or any local process that reads the token,
  can request an excluded file by name and its contents land in `chunks` and `chunks_fts`,
  after which `/query` returns them. The same path reads an arbitrarily large in-repo
  file into memory. Suggested fix: pass every targeted entry through
  `_classify_candidates` (or at least `_is_excluded` plus a size stat) after containment
  validation, and drop or reject entries that fail. `tests/test_targeted_refresh.py` has
  no exclusion or size case. Evidence: rung 3, coordinator-traced through both refresh
  paths.

- **2.3** `[corr]` `builder.py:1554-1567`, `:494-513`, `:580-584` - `_detect_dirty_files`
  records a path only when `git hash-object` returns a truthy SHA and skips it when
  `full.is_file()` is falsy. `_git_cmd` returns `None` on non-zero exit, missing binary,
  or a 10 s timeout; `Path.is_file()` returns `False` on any transient `OSError`. A file
  that is untracked or staged-only exists only in `dirty_map`, never in `git ls-tree`
  output, so on such a failure it is absent from `blob_map`, from `current_files`, and
  from `stat_failed` (which is only computed over `blob_map` keys). Line 513 computes
  `deleted = stored_paths - current_files - stat_failed`, and lines 583-584 delete its
  chunks and file hash. For a modified tracked file the failure is quieter: it keeps the
  committed SHA, `is_dirty` is `False`, the committed blob is read and stored as the
  file's content and hash, and the working-tree edit is dropped and compares as unchanged
  thereafter. Why it matters: one slow `git hash-object` erases a previously indexed file
  from the index. This is the same transient-failure-as-negative class that d43b373 and
  b670b8a fixed for stat and `git status`. Suggested fix: have `_detect_dirty_files`
  return an uncertain set alongside `dirty` (or raise `_DirtyDetectionError` per path),
  and subtract that set from `deleted` and from the `is_dirty=False` blob-read path, the
  way `_classify_candidates` already does. Evidence: rung 3, coordinator-traced.

- **2.4** `[corr]` `[arch]` `builder.py:1539-1555` - Porcelain path quoting is not
  decoded. `git status --porcelain` without `-z` C-quotes any path with non-ASCII bytes
  (`"caf\303\251.blade.php"`); `path = line[3:]` keeps the quotes, `full.is_file()` is
  `False`, and the entry is skipped. That feeds finding 2.3's deletion path
  deterministically on every refresh. The rename branch has the same defect. Why it
  matters: a repository with any non-ASCII untracked or modified filename loses or never
  gains that file's index entries, and a modified tracked one is indexed stale. Suggested
  fix: `git status --porcelain -z` split on NUL (also removes the ` -> ` ambiguity), or
  `-c core.quotePath=false`. Evidence: rung 2. Severity: the architecture worker rated
  this low and the correctness worker high; coordinator keeps high because the loss is
  deterministic and silent, not transient. `[unconfirmed]` whether `git ls-tree -r
  --format=%(path)` applies the same quoting to the tracked side; a run against a repo
  with a non-ASCII tracked path would settle it.

- **2.5** `[arch]` `[corr]` `builder.py:253`, `:257-272`; contrast `:443-466`, `:644-648`,
  `:1201-1226` - `_build_core` calls `self._flush_vectors(store, batch)` and discards the
  boolean. `_flush_vectors` swallows every exception and returns `False`. Both refresh
  paths capture that into `vec_ok` and persist `meta["vec_dirty"]` so the next cycle
  re-embeds; the build's meta block never writes `vec_dirty`. Why it matters: a transient
  model failure during `sr index` publishes an index via atomic swap with missing vectors.
  `_vec_dirty_paths` returns empty, every file compares as unchanged on the next refresh,
  and nothing backfills. Vector search is silently degraded to FTS-only for those chunks
  until a manual full rebuild; the only signal is `embed_coverage` in meta, which nothing
  reads. The same hole applies if `_get_vec_conn()` starts failing mid-build:
  `insert_vectors` returns early (`store.py:1169-1171`) and `_flush_vectors` still
  returns `True`. Suggested fix: accumulate failed batches' paths in `_build_core` and
  write `meta["vec_dirty"]` on the same seam the refresh paths use, or fail the build.
  Evidence: rung 3, coordinator-verified. Both workers flagged it (arch high, corr
  medium); coordinator keeps high.

- **2.6** `[perf]` `builder.py:541-545` -> `:653-681` -> `store.py:768-786` -> `:1515-1521` -
  When nothing changed (`total_changed == 0 and unchanged`), the git-object refresh loops
  over every indexed file calling `_update_branches_only`, which runs a `SELECT` on
  `chunks`, a `get_file_hash`, and an unconditional `upsert_file_hash`. That loop is not
  inside `store.batch_mode()`, so `upsert_file_hash` -> `_auto_commit()` sees
  `_batch_depth == 0` and issues one `COMMIT` per file. The refresh store is opened with
  `build_mode=False`, so `synchronous` stays FULL and each commit is an fsync. Why it
  matters: this is the common case. The daemon tick (`refresh_interval_s` default 300,
  `daemon.py:298`) and every `sr ask` with `auto_refresh=true` (`cli.py:362`, the
  default) run it. On a 10,000-file repo a no-op refresh performs about 20,000 `SELECT`s,
  10,000 `INSERT OR REPLACE`s, and 10,000 fsync'd commits to change nothing. Suggested
  fix: wrap the loop in `store.batch_mode()`, and skip `upsert_file_hash` when the stored
  branch already matches. Evidence: rung 3, coordinator-verified (no enclosing
  `batch_mode` in `refresh()` at `:325-337` or in `_try_git_object_refresh` before the
  loop). The I/O counts are arithmetic, not measured.

Architecture and correctness:

- **2.12** `[arch]` `store.py:713-732`, `:697-711`, `:89-92` - `insert_chunks` uses
  `INSERT OR REPLACE`. SQLite fires `DELETE` triggers for `REPLACE` conflict resolution
  only when `PRAGMA recursive_triggers` is on, which `open()` never sets (`:401-406`). The
  dedup guard snapshots `existing_branches` once before the loop, so a `chunk_id` that
  appears twice within one batch hits `REPLACE` against a row inserted moments earlier:
  the old row is deleted without `chunks_ad`, the new one inserted via `chunks_ai`,
  leaving an orphan `chunks_fts` entry. The orphan is hidden by the `JOIN chunks` in
  `fts_search` (`:872`) but still occupies one of the 30 BM25 slots and breaks
  external-content integrity for that index. Suggested fix: `PRAGMA recursive_triggers =
  ON` on the write connection, or explicit `DELETE` + `INSERT`, or dedupe by `chunk_id`
  at the top of `insert_chunks`. Evidence: rung 4 for the mechanism, coordinator-run.
  Inserting two `ChunkData` with identical path, symbol, and content in one
  `insert_chunks` call gave `chunks` rowids `[2]` and `MATCH` rowids `[1, 2]`;
  `fts_search` returned 1 row. Reachability from `_chunk_text_fallback` (two identical
  paragraphs in one file) is `[unconfirmed]`: my sample file produced a single merged
  chunk, so the duplicate-in-one-batch condition may need a larger or differently shaped
  file.
- **2.13** `[arch]` `querier.py:271-281`; `store.py:527-569`; `builder.py:98`, `:323` -
  `IndexQuerier._open_store` calls `run_migrations()` on a plain read connection. Every
  other schema/data writer first takes `IndexStore.acquire_lock`. `run_migrations`
  executes `ALTER TABLE` and `DROP/CREATE TRIGGER`. Opening `sr ask` against an
  older-schema index performs DDL concurrently with a builder that holds the lock and
  believes it is the sole writer. Idempotent DDL plus WAL make it mostly survivable, but
  the documented invariant (writers take the lock) is not enforced. Suggested fix:
  acquire the PID lock around `run_migrations` in `_open_store`, or make the read path
  raise `SchemaVersionError` when the on-disk version is behind. Evidence: rung 2.
- **2.14** `[arch]` `daemon.py:893-911`; `querier.py:380` - On multi-repo fan-out each

- **2.15** `[corr]` `daemon.py:424`, `:535`, `:552`, `:846-850`, `:938`; mutators

- **2.16** `[corr]` `__init__.py:265-271`, `:239-241`, `:142-149` - `_with_querier`
  escalates to `acquire_write()` and calls `_ensure_querier()` inside the lock, which

- **2.17** `[corr]` `store.py:246-252` - `_acquire_lock`'s stale-lock clause catches

## 3. Code audit - source-recall (both families)

Scope: whole repository. Families: deepen (interface shape) and drift (knowledge

### High

#### 3.1 Repo resolution: `RepoManager.resolve()` as the one owner of "which repo does this request mean"
**Smell:** Callers reaching past the API; Callsite boilerplate; Reconstructed meaning; Parallel vocabularies (already diverged)
**Evidence:** `RepoManager`'s interface (`repo_manager.py:188-190`) is `add / remove / get / list_repos / snapshot_repos / close_all / from_config` plus a public mutable `slots` dict, and no operation for the question every route asks. The copies have diverged: three wordings for "not ready" (`daemon.py:452`, `:879`, `:957`); `refresh`'s 404 at `:950` drops the `Available: [...]` suffix; `server.py` has no 503 branch; and with `repo=None` and zero ready repos, `_resolve_index` and `/query` return 503 "No repos ready" while `/refresh` falls through to 400 "Multiple repos loaded. **Proposal:** `RepoManager.resolve(name: str | None) -> RepoSlot` raising typed `RepoNotFound` / `RepoAmbiguous` / `RepoNotReady`, mapped to 404/400/503 in exactly one place, plus `ready_slots()` for the fan-out path (a snapshot taken under `_lock`). `slots` becomes private. `server.py` builds a `RepoManager` instead of a nested dict; its `state["indexes"]` and the `RepoManager` are two adapters of a two-method registry interface, so the seam is real.
**Payoff:** One definition of the error contract; the 400-vs-503 divergence and the three wordings cannot recur; about 40 lines of branch ladder deleted across two files; the dict race closes as a side effect (rung 2, counted from the four ladders and 31 references; not executed).
**Churn:** `repo_manager.py`, `daemon.py`, `server.py`, one new error type set, plus route tests that pin status codes and detail strings (`tests/test_audit_daemon.py:161` asserts "No repos ready"; `tests/test_server.py` has three `*_requires_repo_when_multiple` tests). Medium risk: the fix changes `/refresh`'s zero-ready answer from 400 to 503, a user-visible change to choose deliberately (rung 2 for the test hits, rung 1 for the line count).

## 5. What is healthy

- **The critique's god-object decomposition landed.** `Index` is 317 lines that resolve config and delegate to `IndexBuilder` / `IndexQuerier` (`__init__.py:170-187`, `:189-209`, `:276-306`). The ten responsibilities enumerated at `docs/history/critiques/architecture.md:52-61` live in `builder.py` and `store.py`, and a query-only consumer can instantiate `IndexQuerier` directly.
- **The refresh delete/re-index sequence is crash-safe by construction.** `_reindex_file_preserving` (`builder.py:714-771`) captures old vector ids before the delete, wraps delete+insert in a nested savepoint via re-entrant `batch_mode`, and distinguishes `_ChunkFailedError` (roll back, keep prior index) from storage failures (propagate, abort). The reasoning is written at each site.
- **Uncertainty is a first-class state in change detection.** `_classify_candidates` (`builder.py:856-905`) returns the uncertain set separately, all three deletion computations subtract it (`:513`, `:1282`, `:1345`), `_positively_absent` (`:816-835`) exists because `Path.exists()` cannot distinguish ENOENT from EACCES, and `_DirtyDetectionError` fails closed on both paths. The findings in section 2 are the paths that bypass this gate, not defects in it.
- **The auth-token lifecycle is genuinely hardened.** `load_or_create_token` writes to a random temp with `O_CREAT|O_EXCL|O_NOFOLLOW` at 0600, loops on short writes, verifies on the descriptor, and publishes via `os.link` for single-winner election; reads re-verify regular-file and owner uid on the fd (`daemon_config.py:225-344`). Comparison is `secrets.compare_digest` (`daemon.py:212`). `/docs`, `/redoc`, `/openapi.json` are disabled on the daemon because they sit outside the auth dependency (`daemon.py:376-381`).
- **SQL is uniformly parameter-bound.** Every statement in `store.py`, `querier.py`, and `builder.py` uses `?` placeholders; the only f-strings in SQL text are generated placeholder counts (`store.py:689-691`, `:1057`, `:1336`) and integer-derived savepoint names. `_fts_escape` (`store.py:1550-1573`) neutralises FTS5 operators and column filters.
- **`trust_remote_code` is gated fail-closed.** `_verify_model_integrity` (`embedder.py:263-355`) requires a 40-hex commit SHA, checksums `config.json`, derives the executed `auto_map` modules from the verified config, checksums each, and verifies the transformers dynamic-module cache.
- **Path containment on the one network-supplied path list is correct and tested.** `_validate_repo_relative` (`builder.py:1603-1629`) rejects empty, NUL, absolute, `..`, and symlink escapes, with seven tests in `tests/test_refresh_path_traversal.py`.
- **The connection-lifetime race the critique predicted is closed with a real primitive.** `ReaderWriterLock` is writer-preferring and used on both sides of the seam; `IndexQuerier._enter_store` drops the cached reference before closing so a failed reopen cannot leave a closed store cached (`querier.py:219-239`); the atomic-swap self-heal via inode signature (`store.py:412-440`) removes the 60-second stale window the critique flagged.
- **Parser and encoding caches remove the two classic chunker quadratics** (`chunker.py:2584-2603`, `:2686-2701`, with an identity check and a reset in `chunk_file`'s `finally`); the graph-expansion N+1 is fixed with a batched, capped, quality-ranked `lookup_symbols` (`store.py:1020-1084`); optional stages short-circuit at zero cost (`__init__.py:138-140`, `querier.py:497`, `:525`); the model load runs on a background thread with double-checked locking (`embedder.py:156-203`).
- **Test discipline where it was applied is the right kind.** FTS trigger coverage is behavioural (`tests/test_store.py:1076-1160`); atomic-swap ordering is verified as a call sequence (`:1179-1251`); identity verification tests the fork-with-same-root-commit case (`tests/test_builder.py:402-413`); polling is bounded and load-tolerant (`tests/test_periodic_refresh.py:19-35`); the daemon auth/host contract is enforced by one `TestClient` fixture (`tests/conftest.py:107-140`); storage isolation is asserted (`tests/test_list_clean.py:60`, `tests/test_fixtures.py:8-16`).
- **No dead top-level functions in `src/`.** Graph cross-check: 150 `Function` nodes, 131 with inbound calls; the remainder are the 16 Typer command handlers and the three ref extractors reached through `_ref_extractor_for`.
